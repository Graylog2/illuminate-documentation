AWS S3 Pack

Amazon S3 is an object storage service. This pack processes two S3 log families: AWS

CloudTrail S3 data events (event_source=s3.amazonaws.com) and S3 server access logs.

Messages are normalized into the Graylog Information Model (file.create,

file.delete, file.access, audit.policy, audit.default) with Security

Core coverage, and a lightweight single-event detection flags CloudTrail cross-bucket

CopyObject operations as potential data exfiltration (301001 host_dlp_detection).

Supported Version(s)

  • AWS CloudTrail S3 data events (CloudTrail record version 1.08 and 1.09)

  • AWS S3 server access log format (current version as of April 2026)

Requirements

  • Graylog 7.1+ with a valid Enterprise license

Log Collection and Delivery

This pack parses logs from the following sources:

  • AWS CloudTrail S3 data events forwarded via the AWS CloudTrail input, the AWS Kinesis/CloudWatch input, or an S3-to-Graylog forwarder

  • AWS S3 server access logs parsed by a forwarder (Lambda or similar) that reads the log bucket and forwards GELF/JSON messages

CloudTrail Delivery

  1. Enable data events for the S3 buckets of interest in a CloudTrail trail. See the AWS documentation on logging data events.

  2. Forward the trail to Graylog using the AWS Kinesis/CloudWatch input, or decode the trail objects and forward them as JSON/GELF.

  3. Preferred contract: deliver each decoded CloudTrail S3 data-event record as the raw JSON object in the message field (one record per message), exactly as it appears in the trail (nested userIdentity, requestParameters, eventSource, eventName, ...). The pack's 06-aws_s3_cloudtrail_parse rule parses that JSON and flattens the nested objects into the canonical fields the normalization stage consumes (event_source, event_name, user_identity_userName, request_parameters_bucketName, source_ip_address, ...). See resources/cloudtrail_s3_log.txt for the exact record shape.

  4. Alternatively, a forwarder may pre-flatten the record to those same canonical top-level field names; in that case the stage-6 parse is a no-op and the pack normalizes the pre-split fields directly.

  5. AWS CloudTrail input shape: the Graylog AWS CloudTrail input (and SNS/SQS pipelines that mirror it) pre-flattens the record with its own field names rather than the canonical ones -- identity arrives as user_name, user_principal_id, user_account_id, user_principal_arn, user_type; the request source IP arrives as source_address (not source_ip_address); and bucketName, key, and x-amz-copy-source are delivered inside full_message instead of requestParameters. The pack's 07-aws_s3_cloudtrail_input_parse rule maps these into the canonical user_identity_* / request_parameters_* / source_ip_address fields and also extracts additionalEventData (a brace-wrapped key=value map) into vendor_data_* fields. No forwarder-side renaming is required for this shape.

  6. Identification: the pack recognizes a CloudTrail S3 event either by the raw JSON record (a JSON object that references s3.amazonaws.com) or by the pre-flattened event_source=s3.amazonaws.com + event_name fields; source=aws-cloudtrail is NOT used as an identifier because that label also carries non-S3 services.

S3 Server Access Log Delivery

  1. Enable server access logging on each bucket you want to monitor. See the AWS documentation on server access logging. Route the access logs to a dedicated logging bucket.

  2. Deploy a forwarder that reads each new log object, parses the space-delimited access log format, and forwards one GELF/JSON message per access record. The typical pattern is an AWS Lambda function triggered by S3 ObjectCreated events on the logging bucket that parses the record and POSTs to a Graylog GELF HTTP input.

  3. The forwarder MUST produce the canonical field triple that the pack's identification rule looks for: bucket_owner, bucket, and operation. With those three fields present, no source label is required. As a fallback the pack also recognises source=s3-access-log-forwarder.

  4. Map every field in the AWS access log record to a top-level message field. Required fields (pack will not categorize without them): bucket_owner, bucket, operation, remote_ip, requester (ARN or canonical-user-id; - when anonymous), key (- when N/A), http_status. Recommended fields: request_id, request_uri, error_code, bytes_sent, object_size, total_time, turnaround_time, user_agent, referer, version_id, host_id, signature_version, cipher_suite, auth_type, host_header, tls_version.

  5. Do not rename vendor field names on the way in -- the pack's rename stage expects the AWS canonical names. In particular: keep remote_ip (not source_ip), requester (not user), key (not file_name), http_status (not http_response_code). The pack's 10-aws_s3_access_log_processing rule performs the rename into Graylog schema fields.

  6. Set short_message (or message) on the forwarded record so Graylog accepts it; a concise summary like remote_ip operation bucket/key works well.

  7. Use a GELF input (HTTP/TCP/UDP) for lowest parsing overhead; a Raw/Plaintext HTTP input works as long as the forwarder emits JSON with the above field names.

  8. For a minimal reference, see the s3_access_log_forwarded.txt example under resources/ -- it shows the exact shape the pack expects after forwarding.

What is Provided

  • Rules to parse, normalize, and enrich AWS S3 CloudTrail data events and S3 server access logs.

  • GIM categorization for S3 object create, access, delete, audit policy change, audit default, and cross-bucket data exfiltration detection.

  • Security Core coverage for file and audit categories.

Events Processed by This Technology Pack

The content pack supports the following log types.

  • AWS CloudTrail S3 data events (PutObject, GetObject, HeadObject, CopyObject, DeleteObject, DeleteObjects, ListObjects, REST.PUT.BUCKETPOLICY, and similar)

  • S3 server access log operations (REST.PUT.OBJECT, REST.GET.OBJECT, REST.DELETE.OBJECT, REST.POST.MULTI_OBJECT_DELETE, REST.GET.BUCKET, REST.PUT.BUCKETPOLICY, and similar)
