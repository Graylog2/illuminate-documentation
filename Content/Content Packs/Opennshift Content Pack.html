OpenShift Content Pack

Red Hat OpenShift is an enterprise Kubernetes container platform. This technology pack processes OpenShift / Kubernetes container log messages delivered as JSON. The initial release normalizes the JSON envelope and Kubernetes / OpenShift metadata -- container name/id, namespace, pod, worker node, container image, and cluster id -- into Graylog schema compatible fields, promotes the human-readable application message to the stored message field, and normalizes the log level to a standard event severity. Application specific message bodies (for example Spring Boot, Kafka, or Django logs) are left intact for parsing in a future iteration.

Scope: this pack focuses on application (container stdout/stderr) logs, identified by log_source "container". It does not process OpenShift audit logs (kube-apiserver, openshift-apiserver, OVN, or node auditd) or node / infrastructure logs -- those records carry no container metadata and are intentionally skipped. Coverage for those log types may be added in a future iteration.

Requirements

  • A Red Hat OpenShift or Kubernetes cluster emitting container logs as JSON

  • Graylog version 7.1 or later

  • A log collector (for example Vector or Fluentd) shipping container logs to Graylog

Supported Versions

  • OpenShift 4.x container logs in the OpenShift Logging (ViaQ) JSON data model, as emitted by a Fluentd or Vector based collector

  • Not supported: the OpenTelemetry (OTEL) log data model introduced with OpenShift Logging 6.x (resource attributes, severityText, body). Configure the collector to forward the ViaQ JSON data model, or wait for OTEL support in a future iteration.

Log Collection and Delivery

OpenShift container logs are collected on each node and shipped to Graylog as JSON by a log collector such as Vector or Fluentd, using the OpenShift Logging (ViaQ) data model. Delivery is supported over Beats, GELF, or syslog. Identification is input-based: dedicate a Graylog input to OpenShift and map it to "openshift" in the core input_routing lookup, or route the logs in with a pipeline routing rule (RoutedFrom). When the JSON is delivered over syslog and a priority/header precedes it, the header is stripped before parsing. Each record carries the cluster id, Kubernetes pod / namespace / container / node metadata, the container stream (stdout or stderr), and the log level alongside the application log line. The OpenTelemetry (OTEL) data model introduced in OpenShift Logging 6.x is not yet supported; configure the collector to emit the ViaQ JSON data model.

Input Routing Setup

OpenShift logs are identified by the Graylog input they arrive on rather than by their payload, so a dedicated input must be mapped to this pack in the core input_routing lookup. Map the input ID to "openshift" so that every message on that input is processed as an OpenShift container log.

  1. Create a dedicated input in Graylog for your OpenShift logs (GELF, Beats, or Syslog, depending on how your collector ships them).

  2. Once created, click Show received messages to open a search window on the input.

  3. Copy the gl2_source_input value from a received message.

  4. Navigate to Enterprise, Illuminate, and click on the Customization tab.

  5. Locate the lookup_adapter_input_routing title and click Edit.

  6. For the content_name key, enter openshift and for the input_id value, enter the gl2_source_input ID copied earlier.

  7. Click Configure value to confirm.

  8. All logs sent to the configured input are now identified as OpenShift container logs and processed by this pack.

  9. Repeat for additional OpenShift inputs as needed.

  10. Alternatively, set or create a static field RoutedFrom with the value Route - OpenShift Logs instead of using the input_routing lookup.

Configuring OpenShift Log Forwarding

This pack processes OpenShift / Kubernetes container logs delivered in the OpenShift Logging (ViaQ) JSON data model: records with log_type set to "application" and log_source set to "container", carrying the kubernetes metadata object and the openshift.cluster_id field. Configure OpenShift Logging to forward these container (application) logs to the Graylog input you mapped under Input Routing Setup. Audit logs (kube-apiserver, openshift-apiserver, OVN, node auditd) and infrastructure / node logs are out of scope for this pack and do not need to be forwarded.

Forward Container Logs from OpenShift Logging

Configure the OpenShift Logging collector (Vector or Fluentd) to forward application / container logs to Graylog. Refer to Red Hat's OpenShift Logging "Configuring log forwarding" documentation for the exact procedure for your OpenShift version.

  1. Install the Red Hat OpenShift Logging operator and deploy a collector (Vector is the default; Fluentd is also supported).

  2. Create a Graylog input for the OpenShift logs (GELF, Beats, or Syslog) and map it to openshift as described in Input Routing Setup above.

  3. Create or edit a ClusterLogForwarder custom resource.

  4. Define an input that selects the application log source. This is the container stdout / stderr stream this pack processes; do not forward the audit or infrastructure sources.

  5. Define an output that points at your Graylog input, using a transport supported by that input (a syslog output to a Graylog Syslog input, or a Vector / Fluentd GELF or Beats output to the matching input).

  6. Keep the default ViaQ JSON data model. Do not enable the OpenTelemetry (OTEL) data model introduced in OpenShift Logging 6.x, which this pack does not yet support.

  7. Add a pipeline in the ClusterLogForwarder that connects the application input to the Graylog output, then apply the resource.

  8. Verify that container log records arrive on the Graylog input and that event_source_product is set to openshift.

Warning: Only the ViaQ JSON data model is supported. If the collector forwards the OpenTelemetry (OTEL) data model (resource attributes, severityText, body), the logs will not be parsed by this pack.

Stream Configuration

This technology pack includes 1 stream:

  • Illuminate:OpenShift Messages

Hint: If this stream does not exist prior to the activation of this pack then it will be created and configured to route messages to this stream and the associated index set. There should not be any stream rules configured for this stream.

Index Set Configuration

This technology pack includes 1 index set definition:

  • OpenShift Logs

Hint: If this index set is already defined, then nothing will be changed. If this index set does not exist, then it will be created with retention settings of a daily rotation and 90 days of retention. These settings can be adjusted as required after installation.

What is Provided

  • Input-based identification of OpenShift / Kubernetes container JSON logs

  • Normalization of container metadata into the container_* schema fields (name, id, namespace)

  • Worker node mapping to host_hostname

  • Kubernetes / OpenShift metadata normalized to the container_* schema fields (image, iostream, pod name/uid/ip/owner, cluster id, app)

  • Promotion of the application message to the stored message field, including containers that use structured JSON logging with no top-level message

  • Log level normalized to event_severity and event_severity_level

  • Parsing of uvicorn / Starlette HTTP access lines into the SDM http_ and source_ fields (source_ip, source_port, http_request_method, http_request_path, http_version, http_response_code)
